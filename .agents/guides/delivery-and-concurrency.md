# 写回、交付与并发

## 写回检查

在任何 `ingest`、`deepen`、`distill`、`verify`、`refactor` 或普通 `maintenance` 结束前确认：

- 主张已回到正确证据等级，关键机制重读过一手 PDF。
- 新页链接出去，相关页也反链回来；无断裂相对链接、孤儿页面或孤儿资产。
- 新增页面或入口摘要变化已同步 `wiki/index.md`。
- `wiki/log.md` 已追加正确、简短的标题和条目；单条超过约 8 行时把实质推导迁回页面。未改原始材料时明确 `raw/` 未改。
- 读者正文没有 raw 行号、`pdftotext`、草稿日期等内部工具痕迹。
- 图表依赖已按视觉规范内嵌。质量剔除遵循其专门例外，不保留日志痕迹。

本仓库没有自动测试；对 Markdown 变更至少检查渲染、frontmatter、相对链接和图像引用。使用 `rg` 做发现，使用 `git diff --check` 检查空白错误。

## Git 与提交

- 每次实质性 wiki 改动后，在回复末尾简短询问用户是否提交和推送；纯查询不问。用户连续讨论时合并自然的一组改动再问。
- 用户同意后，只暂存本会话产生的文件，使用 `docs:` scope 提交信息并推送 `main`。提交消息应遵守仓库的 Lore trailers：记录约束、拒绝的替代方案、置信度、风险、前瞻指示及验证缺口。
- Pull Request 说明写明改动、来源、更新页面与未解矛盾；只有影响视觉资产时附截图。
- 提交前总是检查 `git status`，不要把他人留下的 `M`、`??` 或 `.omx/` 误纳入。

## 并发会话

`wiki/index.md`、`wiki/log.md`、概念页和比较页是共享文件，易被不同会话覆盖：

1. 来源页、模型页、资产通常可独立提交；推送前 `git pull --rebase`。若未提交改动阻塞，先提交或暂存自己的改动。
2. 共享文件宜在并发收口后由一个会话统一写回；或每个会话先 rebase 最新 `HEAD`，只提交自己的几行。
3. 不修改别人的未提交 hunk。普通 `log.md` 仅追加；避免 CRLF/LF 使全文件误变更。
4. 提交前确保每个新 source / model 有 `index.md` 入口与对应日志，否则会产生“有页无索引”的窗口。
